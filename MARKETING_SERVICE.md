# Structured marketing service

Status: ingestion foundation with authenticated APIs and configurable rules,
not a live Google account integration.
The module accepts GA4 Data API report responses, Search Console Search Analytics
responses, and generic structured observations. It stores daily facts in the
existing Postgres database and exposes a deterministic opportunity detector.
No embeddings are generated. Natural-language previews reuse the configured chat
utility model. Scheduled syncs and Google account connections are not included.

## API and frontend flow

All endpoints require the existing authenticated user dependency and a
`workspace_id` query parameter. Members can read and preview. Only workspace owners
can save settings. Workspace identity never comes from generated model output.

| Method and path | Parameters / behavior |
| --- | --- |
| `GET /marketing/data` | Required `source`, `property_id`, `dataset`, `start`, `end`; optional JSON `dimensions` exact filters, `limit`, `offset` |
| `GET /marketing/rules` | Paginated saved rule configurations and revisions |
| `GET /marketing/rules/{rule_id}` | One saved rule plus a deterministic explanation |
| `POST /marketing/rules/preview` | Interpret natural-language target; returns a draft or clarification, never saves |
| `PUT /marketing/rules/{rule_id}` | Save a manual or previewed rule; UUID supplied by client |
| `GET /marketing/opportunities` | Required `rule_id`; optional inclusive `end`, `limit`, `offset`; evaluates the saved rule |

List responses contain `data`, `limit`, `offset`, and `next_offset` (null when done).
Limits default to 100 and cannot exceed 1000. Data windows cannot exceed 366 days.
Data rows retain all dimensions, metrics and ingestion timestamps. For example,
pass `dimensions={"landingPage":"/pricing"}` (URL encoded by the HTTP client) to
filter GA4 records at that exact dimension value. Rows are daily facts, not totals;
do not sum non-additive metrics such as distinct users or rates in the frontend.

For a human-entered target, POST to `/marketing/rules/preview?workspace_id=...`:

```json
{
  "text": "Find queries containing invoice, excluding Acme, with at least 500 impressions, CTR below 3%, positions 1 to 15, over 28 days.",
  "property_id": "sc-domain:example.com",
  "dataset": "query-page-web-v1"
}
```

A successful response contains `status: "ready"`, `rule`, `summary`, `assumptions`,
`questions: []`, and `saved: false`. Display the summary, assumptions and editable
fields. The summary is generated by deterministic code from validated settings.
An ambiguous/unsupported target returns `status: "needs_clarification"`, a null
rule and questions. Re-submit the full clarified target; previews are stateless.
Model interpretation can make mistakes, so the displayed rule is the executable
meaning the human saves. General aspirational goals such as growing revenue 20%,
semantic keyword matching, and new detector types are not implemented.

Save through PUT `/marketing/rules/{client-generated-uuid}?workspace_id=...`:

```json
{
  "expected_revision": 0,
  "rule": {
    "name": "Invoice search opportunities",
    "property_id": "sc-domain:example.com",
    "dataset": "query-page-web-v1",
    "enabled": true,
    "min_impressions": 500,
    "ctr_threshold": 0.03,
    "position_min": 1,
    "position_max": 15,
    "window_days": 28,
    "keywords": {
      "mode": "contains",
      "include": ["invoice"],
      "exclude": ["acme"]
    }
  }
}
```

Use the preview's complete `rule` object to preserve the original `target_text`.
`expected_revision: 0` creates a rule. Updates require the revision returned by
GET/PUT and increment it atomically. A stale revision returns 409; reload before
editing again. Disable rules with `enabled: false` using the same PUT endpoint.
Disabled rules produce no opportunities and do not fetch observations.

Keywords support `exact` or literal substring `contains` matching. Both include
and exclude lists share that mode. Text is Unicode-normalized and case-insensitive.
Include terms are OR; an empty include list accepts all queries. Any exclusion wins.
Wildcards/regex have no special meaning. Threshold comparisons are impressions >=,
CTR <, and inclusive minimum/maximum average position. CTR is a fraction, so 3%
is stored as 0.03. All fields use validated bounds and reject unknown settings.

Opportunity windows use the saved `window_days`, ending yesterday in UTC unless
an explicit `end` is supplied. The API returns the resolved window, rule revision,
rule settings, evidence and `coverage: "unverified"`. It does not claim complete
or fresh source data. Evaluations exceeding 100,000 daily rows return 422 rather
than silently analyzing a truncated dataset. The endpoint evaluates one saved
rule at a time and paginates the results, ordered by impressions descending.

Errors: 401 for unauthenticated calls, 403 for denied access/edit permissions,
404 for missing workspaces/rules, 409 for edit conflicts, 422 for invalid input,
502 for invalid model interpretation, 503 for unavailable language interpretation.
Structured manual rule editing works independently of the language model.

## Google Ads Keyword Planner

Keyword Planner report imports are supported through a separate research API.
These are estimated market-demand snapshots, not observed daily website metrics.
The initial integration accepts Google Ads REST JSON responses from
`GenerateKeywordIdeas` (`keywordIdeaMetrics`) and
`GenerateKeywordHistoricalMetrics` (`keywordMetrics`). It does not yet connect
to a Google Ads account or generate new ideas directly from seed keywords/URLs.
CSV files from the Google Ads UI are not accepted by this JSON adapter.

Apply `migrations_create_keyword_planner_reports.sql` before using these routes:

| Method and path | Behavior |
| --- | --- |
| `POST /marketing/keyword-planner/reports` | Owner-only import of a complete report with context and a client-generated snapshot UUID |
| `GET /marketing/keyword-planner/reports` | List snapshots by required `customer_id` and `dataset`, with pagination |
| `GET /marketing/keyword-planner/reports/{snapshot_id}` | Read and filter normalized keywords from one snapshot |

All routes require `workspace_id` and the existing authenticated user. Keyword
reads support repeated `include` and `exclude` query parameters, `match=exact`
or `contains`, `min_monthly_searches`, `max_competition_index`, `limit`, and `offset`.
Results sort by average monthly searches descending, with unknown volume last.
Filters use inclusive thresholds. Missing estimates do not satisfy thresholds.

Example import request:

```json
{
  "snapshot_id": "cc34f196-9001-4a27-8d5b-83ae9a7aaac1",
  "captured_at": "2026-09-01T12:00:00Z",
  "report_kind": "historical_metrics",
  "context": {
    "customer_id": "1234567890",
    "dataset": "invoice-keyword-research-v1",
    "language": "languageConstants/1000",
    "geo_target_constants": [],
    "network": "GOOGLE_SEARCH",
    "currency_code": "USD"
  },
  "report": {
    "results": [{
      "text": "invoice automation",
      "closeVariants": ["automate invoices"],
      "keywordMetrics": {
        "avgMonthlySearches": "1000",
        "competition": "LOW",
        "competitionIndex": "20",
        "lowTopOfPageBidMicros": "1200000",
        "highTopOfPageBidMicros": "3000000",
        "monthlySearchVolumes": [{
          "year": "2026", "month": "JULY", "monthlySearches": "900"
        }]
      }
    }]
  }
}
```

Supply the context actually used to generate the report. An empty geography list
represents no geographic restriction; never relabel a worldwide report as local.
Currency must be the originating account's currency. Bid/CPC values remain integer
micros: divide by 1,000,000 for display, using that currency. Competition is paid-ad
competition, not organic ranking difficulty. Null estimates are preserved.

Close variants stay attached to one canonical keyword; their shared metrics are
never duplicated or summed. Keyword include/exclude matching considers both the
canonical keyword and its variants; excluding any variant excludes the whole group.
Monthly history stays within its snapshot and is not added to Search Console data.

Imports are bounded to 10,000 keywords and 8 MB of report JSON. Assemble paginated
idea results before import; a nonempty `nextPageToken` is rejected. A retry using
the same snapshot ID and identical normalized content succeeds. Different content
under the same ID returns 409; use a new ID for a later capture. Imported context
and completeness are supplied by the importer and are not verified against Google.
Never infer a market opportunity solely from the absence of an imported keyword.

Current limitations: Planner filters are research filters, not a second saved
opportunity detector. Natural-language rule previews still support Search Console
CTR rules only. Live ideas/historical-metrics requests, account authorization,
scheduled refreshes, and Planner-specific saved rules remain integration work.
The repository requires the `aws-secrets-manager` skill before credential work;
that skill was not available in the installed skill directories during this change.

Provider references:
[Keyword ideas](https://developers.google.com/google-ads/api/docs/keyword-planning/generate-keyword-ideas),
[historical metrics](https://developers.google.com/google-ads/api/docs/keyword-planning/generate-historical-metrics).

## Why tables first

Counts, dates, conversion rates, comparisons and joins require exact values.
Keep GA4 and Search Console in separate datasets because their attribution,
coverage and reporting semantics differ. Do not infer keyword-level conversions
by joining page conversions onto every Search Console query.

Vectors are optional for grouping related queries, matching queries to page
content, and retrieving supporting business documents. Numerical evidence must
always come from the structured store. An LLM may explain measured signals but
should not invent the measurements or claim that correlations prove causation.

## Internal usage

Apply `migrations_create_marketing_observations.sql` and
`migrations_create_marketing_rules.sql` through the normal database migration
process. The backend database role must have appropriate table access;
RLS is enabled without client policies. Authorize workspace access in the calling
job or route before invoking the service. The module itself is not an auth boundary.

```python
from datetime import date
from app.primitives.marketing import MarketingService, parse_search_console
from app.primitives.marketing.store import PostgresMarketingStore

service = MarketingService(PostgresMarketingStore())
observations = parse_search_console(report_response, ["date", "query", "page"])
await service.ingest(workspace_id, "search_console", "sc-domain:example.com",
                     "query-page-web-v1", observations)
signals = await service.opportunities(
    workspace_id, "sc-domain:example.com", "query-page-web-v1",
    date(2026, 8, 1), date(2026, 8, 28),
)
```

GA4 uses `parse_ga4(report_response)` with a `date` dimension. Other sources
provide `Observation(day, dimensions, metrics)` records. A dataset name must
identify a fixed report definition, including filters, dimensions, search type,
timezone, currency and attribution settings where applicable. Change the dataset
version when those settings change. Never mix totals with detailed rows.

The primary key contains workspace, source, property, dataset, date and a hash of
all dimensions. Repeated observations replace their metrics; duplicate grains
within a batch are rejected. Ingestion is an upsert, not a full snapshot
replacement: rows absent from a later report are not deleted. Callers must not
treat partial report batches as proof that a period is complete.

The initial detector defaults to low-CTR query/page segments with at least 100
impressions and average position between 1 and 10. All thresholds, position bounds,
keyword filters and the evaluation window are configurable. The default 2% CTR
threshold is a heuristic, not an industry benchmark. Counts are summed,
CTR is recomputed, and position is impression-weighted. Country/device dimensions
remain separate. Results include the report identity, date window, evidence and
thresholds. Production prioritization should add comparable historical baselines,
brand/position segmentation, freshness checks and minimum observed days.

## Verification

Run `python -m unittest discover -s tests -p "test_marketing*.py"`.
Tests cover parsers, aggregation, keyword matching, threshold boundaries, language
output validation, workspace access, owner edits, pagination and edit conflicts,
plus Keyword Planner estimates, close variants, nulls, import validation and filters.
Tests use in-memory/mock stores and a mocked model; they do not access Google,
Postgres or live model inference. Apply migrations and validate against the target
database role and configured model before deployment.
